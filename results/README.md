# Results

Every number in the top-level README comes from these files. The `.etl` traces themselves are
not committed (roughly 20 MB each, ~150 traces); `runs.csv` and `attrib.csv` are the extracted
data, `report.md` is generated by `launchlab report`, and `env.json` is the environment the
harness recorded at capture time.

All of it was captured on one machine: Windows 11 Pro ARM64 26200.8037, a VMware Fusion guest
on Apple silicon, 4 vCPU / 8 GB / SSD, Defender real-time protection on.

| directory | what it is |
|---|---|
| `warm-tempfile-capture/` | Batch 1. arm64 vs x64, warm, n=20 each. The harness still captured the workload's stdout to a temp file, which is why the absolute numbers differ from the later batches — and why the stability of the *shift* across both mechanisms is worth something. `runs.csv` only; reconstructed from the two arms after the traces were overwritten. |
| `warm/` | Batch 2. Same comparison after switching to pipes. |
| `warm2/` | Batch 3. Same again, with `cpu_on_ms` added — the decomposition table in the README. |
| `alt/` | Batch 4. Same, with tracing alternated run by run. |
| `hash/` | The heavier workload: both binaries hashing a fixed 32 MB file, n=12 each. |
| `coldxta/` | `C:\Windows\XtaCache` cleared before every run, n=10 per arm, arm64 included as the control. |
| `spike-base/`, `spike-inject/` | Negative control: the same workload with and without an injected 120 ms CPU spin plus a 32 MB flushed write. |
| `overhead/` | First attempt at pricing the recorder, untraced batch then traced batch. Kept because it is the measurement that turned out to be confounded. |
| `settle0/`, `settle2/` | The experiment that explained it: untraced runs with 0 s and 2 s between them, n=15 per arm. `overhead.csv` only — these runs produce no traces. |

To regenerate a report from any of these directories:

```
dotnet run --project src/LaunchLab -- report results/warm2
```
