一份效能量測的白話版

15 毫秒
去哪了？

同一支程式，同一台電腦，只是換成另一種「口音」重新編譯——啟動就慢了 15 毫秒。 我們把它拆開來看，結果三個直覺全錯了。

先搞懂一件事

有些程式，需要一台翻譯機

arm64 版程式 → 晶片 直接聽得懂
x64 版程式 → 翻譯機 → 晶片 每一句都要翻

新的 Windows 筆電用的是 ARM 晶片。舊程式是用 x64 寫的，晶片聽不懂， 所以微軟放了一台叫 Prism 的翻譯機在中間。問題只有一個：翻譯要多少錢？

量出來的答案

每啟動一次，多花 15 毫秒

arm64 版不用翻譯
20.8 ms
x64 版要翻譯
36.3 ms
✓

這個數字很硬：換了四批、用了兩種不同的量測方式， 差距都落在 14.6 – 15.5 ms。 絕對值會飄，但差距不會。

那 15 毫秒的成分

九成是「真的多做了事」

多做的計算 13.9 ms
90% 真的在 CPU 上算東西 3% 排隊等 CPU 7% 其他

差別不是「卡住了」或「在等硬碟」，而是翻譯過的程式指令就是變多了。 而且讓程式多做一點事（改成計算一個 32MB 檔案的雜湊），差距就從 15 ms 變成 28.7 ms—— 是按工作量計價的。

直覺 ①

「一定是翻譯稿被清掉了」——不是

翻譯機會把翻好的稿子存起來，下次直接用。所以大家都猜：把稿子清空，第一次啟動一定很慘。

有翻譯稿
33.8 ms
稿子清光
33.4 ms
✕

完全沒差。去翻了現場才知道為什麼：那些翻譯稿是給系統元件用的， 不是給這支程式；而且是事後才慢慢寫的——程式根本沒在等它。

直覺 ②

最貴的東西，是讓電腦打盹

連續啟動電腦沒停過
19.8 ms
同時在錄影量測工具全開
20.0 ms
先閒置兩秒然後才啟動
55.8 ms

打個盹的代價，是模擬的兩倍。

我們本來想量「打開量測工具會不會影響結果」，答案是幾乎不會（19.8 → 20.0）。 真正把數字弄亂的，是為了「讓機器安靜下來」而刻意加的那兩秒等待—— 為了嚴謹加的東西，變成整個實驗最大的干擾源。

那你怎麼知道尺是準的

先偷偷放一個已知的重量進去

在被量測的程式裡塞進「剛好 120 毫秒的計算」加「寫 32MB 到硬碟」， 再看工具會不會找到、找得準不準。

原本
38.9 ms
塞了東西之後
192.0 ms
✓

多出來的 153 ms 裡，142 ms 被正確歸到「計算」， 10.6 ms 歸到硬碟——而且直接點名是哪一個檔案。 尺是準的。

一句話

值錢的不是數字，是那三個「不是」

翻譯確實要錢，一次 15 毫秒，九成花在多做的計算上。 但不是快取的錯、不是量測工具的錯——而在你以為無害的那兩秒等待裡， 藏著比要研究的東西還大兩倍的干擾。

量測環境：Windows 11 ARM64（26200.8037），跑在 Apple 晶片上的虛擬機，4 核心 / 8GB / SSD， 防毒即時掃描全程開著。每組 20 次、交錯執行、取中位數。
